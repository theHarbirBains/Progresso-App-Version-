# Progresso — Design System (DESIGN.md)

This document is the **visual source of truth** for Progresso's mobile app. It describes the design system as it actually exists in code today — tokens, components, and conventions — not an aspirational redesign. Read this before making any UI change; do not invent colors, typography, spacing, radii, or component patterns that conflict with what's documented here. If a screen needs something not covered here, extend the existing token/component system rather than hand-rolling a one-off value, and flag the gap rather than silently improvising.

Source files this document is derived from: `apps/mobile/src/design/theme.ts`, `apps/mobile/src/theme/accentColor.ts`, every component in `apps/mobile/src/design/` (in particular `GlassBackground.tsx`, `AppBackgroundLayer.tsx`), `apps/mobile/src/settings/settingsStyles.ts`, `apps/mobile/src/design/UnderlineTabs.tsx`, `apps/mobile/src/navigation/navigationTransitions.ts`, `apps/mobile/src/charts/LineChart.tsx`, and `apps/mobile/src/workouts/MuscleVisualization.tsx`.

## 1. Visual Philosophy

Progresso's internal design direction is **"Warm Minimal"** — warm charcoal and near-black surfaces, warm off-white text, and one soft amber accent, with the natural light of a warm gym photograph behind the one hero card on a screen. It is a restyle of the earlier "Dark Glass" direction (and its black-and-white phase), not a new structure: every layout, component and spacing rule below is unchanged. The app is dark-mode-first and dark-mode-only (see §2), still built on one accent color doing all the visual "work" (primary actions, key numbers, active states, PR highlights) against a near-black backdrop — but that backdrop now has real depth: a cinematic background layer (§3a) with a soft vignette, and most structural surfaces (cards, navigation, modals, controls) are **translucent glass** sitting on top of it (§3b) rather than flat opaque fills. The feel is still closer to a fitness-tracking instrument panel than a consumer social app: numeric values keep their distinct monospace "readout" treatment (§5) to feel measured and precise, while everything else uses a single humanist sans-serif.

A deliberate simplicity rule still threads through the whole system: one accent color per context (not a rainbow of semantic colors), one card treatment (plus a rare "hero" variant), one radius scale, one spacing scale, and now one glass-surface treatment (§3b) reused everywhere rather than each screen inventing its own translucency. New UI should extend that consistency, not introduce a parallel one.

Where each part applies: **every screen has the same background** (§3a) -- the theme's photo across the top (the warm gym photo in the default, Golden Hour Gym), darkened for legibility and fading into the warm near-black fill, with a soft glow of the theme's accent. **Themes are curated, never free-form** (§3c): a theme is one photo and one accent chosen together, and everything else -- surfaces, text, charts, forms, the live workout -- stays the same warm dark in every theme, so the app always looks as designed. **Glass is reserved** for grouped or actionable surfaces (`AppCard`) and structural chrome (bottom nav, side menu, sheets). A screen's content is **sections, rows and numbers by default — a card only where it earns its place** (§10, §17). The interface is one typeface plus mono readouts (§5), one bottom navigation (§11), and one set of shared primitives (`Screen`, `Section`, `ListRow`, `Stat`, `Button`, `Skeleton`) that every screen composes from.

The relationship that gives every screen its depth, and that any new UI should preserve:

```
BACKGROUND (AppBackgroundLayer / ScreenBackdrop: warm fill → gym photo fading into it → glow and shade)
  ↓
TRANSLUCENT GLASS (GlassBackground: tint + optional blur + hairline border)
  ↓
CONTENT (strong primary text, muted secondary text — §5)
  ↓
ACCENT (restrained — selected states, primary actions, key numbers — §4)
```

## 2. Dark/Light Appearance

**There is no light mode.** Progresso ships a single, fixed dark palette (`apps/mobile/src/design/theme.ts`). There is no `useColorScheme`, no `prefers-color-scheme` handling, and no light-mode token set anywhere in the app. Do not add light-mode-conditional styling unless a future task explicitly introduces light mode as a scoped feature — until then, `colors.background` (`#12110F`) etc. are the only values in play.

## 3a. Background System (`AppBackgroundLayer.tsx`)

Mounted **once**, behind the whole app (`App.tsx`'s `AppShell`) — no screen paints its own background; every screen's root `View`/`ScreenContainer`-equivalent is `backgroundColor: 'transparent'` so this shows through. Never hardcode a background color on a screen; the one background below is the same everywhere, with the active theme's photo in it (§3c).

**One background, on every screen.** Every screen is the warm fill (`colors.background`), the golden gym photo (`assets/background-gym-sunset.jpg` — the original workout photo cropped to the gym itself: the window with the sun on the mountain line, the plates down the right, the bench in front; graded golden and high-contrast like the Warm Minimal reference, sharp, the sun's glow bloomed to a hot core, upscaled 1.5× with light sharpening) pinned to the top at the screen's full width, and a soft accent glow with a gentle bottom shade (`Atmosphere` in `AppBackgroundLayer.tsx`). The photo sits behind the header and the first widgets, as in the Warm Minimal reference, and fades into the fill lower down, so lists, charts and the live workout's sets sit on plain warm dark. `AppBackgroundLayer` draws it for the signed-out screens, onboarding included (with no glow, since no mode exists yet); `ScreenBackdrop` draws the identical thing for every screen inside the navigator -- Feed included -- opaque and part of the screen itself, so a push/pop moves it natively and a page transition never depends on JS to change what is behind it. The glow is the one amber accent (§3) whichever mode the route belongs to. The strip behind the persistent bottom nav is the flat fill. **Never make a screen's root opaque or transparent on its own** -- the layer/backdrop is applied once, centrally. The few deliberate exceptions paint their own fill: native `Modal`s (`ExercisePickerModal`, the group editor's custom-exercise modal -- they open in their own window with nothing behind them), the camera, the launch screen and the photo lightbox.

Layered bottom-to-top, on every screen:

1. **Flat fill** — `colors.background` (`#12110F`), in every theme. The old free-form picker (Obsidian/Midnight/Forest/Plum/…) stays gone; a `background_theme` value it saved on an account is ignored. Themes (§3c) change only the photo and the accent.
2. **Photo** — the golden gym photo, `contentFit="cover"` in a box at its own aspect ratio (1278×1950), the screen's full width and pinned to the top: the whole gym in view, the plates down the right edge and the sun near the top right, as in the reference. It is kept sharp — window frames, pines, clouds and mountains — and darkening layers of `colors.background` keep text over it readable: a **side scrim** across the whole screen (62% on the left, where text starts, easing to clear on the right, where the sun is), a **header band** behind the header (30% at the top, gone by 140pt -- the header's icons and Feed's workspace pill sit on their own dark glass, so the band only has to carry a plain title), and down the photo a steady **70%** through its upper part, fading fully into the fill at its bottom edge. Chosen by measurement on a phone-sized screen: `textPrimary` keeps WCAG AA (4.5:1) even over the photo's brightest pixel, `textSecondary` over all but its brightest specks, and text inside a card (§10) at every pixel, so text and widgets can sit anywhere near the top of a screen.
   **The photo in full behind Feed's Next Workout.** While Feed's Next Workout hero shows, the photo's own darkening drops from 70% to **10%** through its upper part (down past the hero's button), darkening below it — so the sunset glows through the see-through hero, as in the reference, with the side scrim and header band still in place. Feed asks for it through `useHeroBackdrop` (a context `ScreenBackdrop` provides), and the photo eases between the two in 300ms (instantly with Reduce Motion) — drawn as the hero darkening plus one "everyday" layer that adds back the 70% darkening at full opacity. Measured the same way: the header keeps AA at every pixel, the hero's title the large-text 3:1, its smaller lines AA over all but the brightest specks, and text in a card AA at every pixel wherever a card scrolls to. Only Feed does this — Train's start card sits right above its calendar and a text link, which the brighter photo would wash out. Don't lighten either state without re-measuring.
3. **Atmosphere** — the accent glow (alpha 0.08 easing to 0 from the top-left, tightly concentrated rather than washing most of the screen) and the bottom shade (0 → 0.28 black), both static.

Glass surfaces (§3b) sit **above** all of these layers — they are a foreground concern, never part of this background stack.

**Text/card contrast** comes from the photo's darkening (above) for text sitting straight on the background, and from each surface's own fill or tint (§3b, §10) for everything inside a card. Glass surfaces read the fixed `colors.surface`/`colors.surfaceRaised` tokens directly. Don't introduce a background/theme system or per-screen backgrounds; the one background above is deliberate.

## 3b. Glass Surface System (`GlassBackground.tsx`)

The one glass-surface treatment, reused everywhere rather than each screen inventing its own translucency. `GlassBackground` is a purely decorative, absolutely-positioned layer — components render it as their **first child**, keep their own existing outer border-radius/`overflow: 'hidden'`, and let it show through. It never wraps content itself (so it never changes hit-testing, layout, or how a consuming component handles `onPress`).

A glass surface is always three things, layered together:

- **Tint** — `colors.surface` (or `colors.surfaceRaised` for the `chrome` variant), at partial opacity (`withAlpha`) — so the surface reads as warm material over the background and its photo, just translucent.
- **Border** — a neutral light-alpha hairline (`colors.glassBorder` / `colors.glassBorderStrong`, §4) that reads as "catching light," rather than each theme's own (much darker) `border`/`divider` tokens.
- **Blur** _(only the `chrome` variant — see below)_ — a real native blur (`expo-blur`'s `BlurView`) behind the tint, giving actual depth-of-field against whatever's scrolling underneath.

**Two variants — this is a performance boundary, not a style choice:**

- **`surface`** _(default)_ — tint + border, **no blur**, at an 80% fill opacity (`widgetFillAlpha` in `theme.ts`, shared with `Card`'s fill, §10) — so the sunset photo stays visible through every widget, as the user asked, while `textPrimary`/`textSecondary` keep WCAG AA over the photo's brightest pixels, Feed's brighter hero state included (measured; it was 70% over the darker earlier photo, 86% and 60% before that). Never a flat opaque fill. Used for repeatable, potentially-many-per-screen elements: `AppCard` (including `hero`, which keeps its own accent-adjacent `surfaceHero`/`borderHero` tint rather than following the per-theme environment), `SegmentedControl`'s track, `IconButton`'s default (non-accent-filled) state. A `BlurView` per instance would be wasted cost at this repetition level — the tint+border alone already reads as glass.
- **`chrome`** — tint + border + real blur, at 80% fill opacity, letting the blur itself (rather than a higher tint alpha) carry most of the grounding against constantly-changing content behind it. Reserved for the handful of **structural, one-instance-at-a-time** surfaces: `BottomNavBar`, `AppSideMenu`, `BottomSheet`. These are exactly the surfaces §11/§15 call for blur on, and bounding real blur to "at most one on screen" is what keeps this affordable on real devices.

**What never gets glass:** `PrimaryButton`/`SecondaryButton`/`DestructiveButton`/`TextButton` (a primary action should read as solid, not diluted — see §8), `TextInput` (an input's fill staying fully opaque is a deliberate readability/accessibility choice — text typed over a blurred, theme-shifting background would be harder to track), `Badge` (already a deliberately light accent-tinted pill, not a "surface"), chart components, small icons/labels on their own. Don't make every element glass — see §20.

**Accessibility**: a glass surface's tint opacity is tuned so `textPrimary`/`textSecondary` sitting on top keep their existing contrast ratios against the darkest theme _and_ the depth overlay's darkened edges — see §19.

## 3c. Themes (Settings > Appearance)

Eight curated themes, each **one photo and one accent**, chosen together (`theme/appThemes.ts`): **Golden Hour Gym** (`#D99A50`, the gym photo -- the original look and the default), **Forest** (`#9DBF7A`), **Alpine** (`#8DB8D6`), **Coast** (`#6FC2B8`), **Spring** (`#E8A0B4`), **Summer** (`#E8B84A`), **Autumn** (`#D9774A`) and **Winter** (`#A9C4E0`). Each photo is cut to the gym photo's proportions (852:1300), graded to sit beside it (golden-hour or dusk light, a touch of contrast and its season's tint, light sharpening) and kept around 300-560 KB; only the active one is ever drawn. Every one sits under the same darkening layers (§3a), which keep `textPrimary` AA over even a pure-white pixel, so ordinary screens are equally readable in every theme. Behind Feed's hero, where the photo shows nearly in full, each theme has its own `heroDarkness`, measured so hero text keeps at least the contrast it has over the gym photo (10%): Summer and Autumn 10%, Spring and Winter 20%, Forest, Alpine and Coast 35%. Every accent keeps 4.5:1 as text on the fill, and its ink is worked out as before (`buildAccentTheme`), tested. Surfaces, text, borders, charts, forms and the live workout never change with a theme. The share card takes the theme's photo and its accent's frame; the Home Screen widgets keep the brand amber.

**Choosing.** Settings > Appearance: the themes as a two-column grid of `ChoiceTile`s -- each the top of its photo with a fade, a dot of its accent and its name, and, chosen, its own accent's edge and check, so a choice previews itself -- then **Change with the seasons** (a `ListRow` with a `Toggle`, off by default): Spring, Summer, Autumn or Winter by month, the other way round for a country south of the equator (the country from onboarding). A theme only ever changes by the person's own choice: picking a theme turns the seasons off, so the pick always shows. Then a muted credit line for the photographers (Unsplash). The choice is applied at once, kept on the phone (`theme/AppThemeProvider.tsx` -- how the app looks here, like a wallpaper, not account data), and read before the first screen shows, so the default never flashes first.

## 3. The Accent (Workout & Nutrition)

The app has **one accent at a time**: the theme's (§3c) -- soft amber, the static brand accent (§4), in the default. It is still delivered per mode, as two `AccentTheme`s (the same one), so every screen reading `theme`/`nutritionTheme` off `useProgressTheme` is unchanged; a shared component given no colour takes the theme's accent too (`useAppTheme`), never the static amber:

- **Workout Mode** accent — `#D99A50` (soft amber)
- **Nutrition Mode** accent — `#D99A50` (soft amber)

Both are the same soft amber — the Warm Minimal redesign's call, replacing the earlier neutral white (and, before that, Workout blue `#2F80FF` / Nutrition green `#10B981`). **There is no free colour picking**: the Workout/Nutrition colour pickers (and their preset palette and RGB slider) were removed because a poorly chosen colour made the app look wrong; an accent only ever comes with its theme, so the bottom nav's highlight of the page you're on, primary buttons and every other accent use are always the theme's vetted accent. A `workoutAccentColor`/`nutritionAccentColor` saved on an account by the old pickers is ignored. Train and Nutrition are told apart by label and icon, not by color. On amber, `onAccent` resolves to the dark ink (`colors.background`).

Every consumption site derives from **one base hex** via `buildAccentTheme(hex)` in `apps/mobile/src/theme/accentColor.ts`, which returns:

| Field          | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accent`       | The base color itself                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `onAccent`     | Text/icon color for content on top of a filled `accent` surface — computed per-color via WCAG relative-luminance contrast against both `colors.background` and `colors.textPrimary`, so a light accent (e.g. Pure White, or the default Warm Amber) correctly gets dark text and a dark accent gets light text. **Never hardcode which ink color goes on an accent — always derive it, or use the value this function already computed.** |
| `accentBg`     | The accent at 14% alpha — tinted backgrounds (e.g. selected tab fill)                                                                                                                                                                                                                                                                                                                                                                     |
| `accentBorder` | The accent at 35% alpha — tinted borders                                                                                                                                                                                                                                                                                                                                                                                                  |
| `accentMuted`  | The accent blended 50% toward `colors.surfaceRaised` — subtle icon backgrounds                                                                                                                                                                                                                                                                                                                                                            |
| `progress`     | Progress-fill color, currently identical to `accent`                                                                                                                                                                                                                                                                                                                                                                                      |

Components that need to _follow_ whichever mode is active (Button's `PrimaryButton`, `SegmentedControl`, `Toggle`, `Badge`, `BottomNavBar`, `MuscleVisualization`) accept `accentColor`/`onAccentColor` props defaulting to the static brand accent — **never a second, competing color system.** A screen passes the resolved `AccentTheme` fields down; a component given none gets the brand default, which is the same amber.

Settings itself (being app-level/global, not per-mode) has no theme of its own — it wears the app theme like everything else.

## 4. Colors & Semantic Usage

All values live in `apps/mobile/src/design/theme.ts`. Never hardcode a hex that duplicates one of these — reference the token.

```
background:      #12110F   // warm near-black app background (Warm Minimal)
surface:         #1C1916   // dark charcoal: standard card/row background
surfaceRaised:   #26211C   // elevated warm surface: Feed/Train cards (at 80%), selected fills, raised chips
surfaceHero:     #211A13   // the ONE hero AppCard per screen only (see below)
borderHero:      #4F3A24
border:          #393129   // subtle warm card/input border
divider:         #2C2620   // row dividers within a card

textPrimary:       #F5F0E8   // warm off-white: headings, primary content, values
textSecondaryBright: #D3CBBF // a brighter step between textSecondary and textPrimary, for secondary text where textSecondary reads too dim
textSecondary:     #B6ADA1   // muted warm supporting text, unselected labels
textMuted:         #7E7569   // placeholders, disabled/empty-state text, icons at rest

accent:          #D99A50   // the single static brand accent -- soft amber (Warm Minimal, replacing neutral white)
onAccent:        #12110F
heroAction:      #F2E3CD   // warm cream fill of the one action on a photo hero Card, with onAccent text

destructive:     #F0555C   // errors, delete actions only
destructiveBorder: #3A2226

chartAccent:     #D99A50
chartMuted:      #393129

glassBorder:       rgba(245, 230, 210, 0.08)   // warm glass-surface hairline, default weight; also Card's edge
glassBorderStrong: rgba(245, 230, 210, 0.14)   // glass-surface hairline, chrome surfaces (§3b)
surfaceLift:       rgba(245, 230, 210, 0.06)   // a raised block inside a widget: StatBlock, FoodFacts' macros, the top-set block, icon wells
```

**Semantic rules:**

- **Warm Minimal, app-wide.** Warm near-black backgrounds, charcoal surfaces, warm off-white text and one soft amber `accent` (also both mode accents, §3) -- a deliberate redesign call, restrained on purpose: amber marks the active tab, primary actions, selected states and key numbers, nothing decorative. Where two things need telling apart (Train vs. Nutrition, a workout vs. a food log in Feed), that's done with label/icon, not hue. There is no free colour picking; a theme's accent comes with it (§3, §3c).
- **One brand accent, no separate "success" color.** Personal records reuse `colors.accent` rather than a green/success hue (an explicit, approved direction — see `Badge.tsx`'s own comment).
- **`hero` is reserved for the single most important card on a screen** (e.g. Workout Detail's summary card, Profile's identity card) — a thin accent-tinted border (`surfaceHero`/`borderHero`) instead of a fill, so elevation reads as "this is the important one" without introducing a second color block. Do not apply `hero` to more than one card per screen.
- **Destructive red is for errors and destructive actions only** — never repurposed as a generic "warning" or "attention" color.
- Numeric "readout" values (`StatValue`, chart lines) default to the brand accent color, distinct from body text.

## 5. Typography

**One typeface, plus mono for numbers.** Fonts are loaded via `useFonts()` before anything renders (`App.tsx`'s `FontGate`):

- **Plus Jakarta Sans** — _all_ text: `body` 400, `displayMedium` 500, `semibold` 600, `display` 700, `displayHeavy` 800. There is no system-font text anywhere; body copy is Plus Jakarta Sans Regular, so the app has one typeface rather than two competing sans-serifs.
- **JetBrains Mono** (`mono` 500, `monoBold` 700) — **numeric "readout" values only** (stat values, PRs, calorie counts, wheel-picker numbers). Never used for prose, labels, or headings. This mono/sans split is a deliberate, approved direction — don't blur it.

**`Text`** (`design/Text.tsx`) is the only `Text` the app uses — a drop-in for react-native's, never imported from `react-native` directly. React Native has no global default font, so without it any string that doesn't name a `fontFamily` falls back to the system font. `Text` resolves in order: an explicit `fontFamily` is left alone (mono readouts, the `typeScale` tokens); otherwise a written `fontWeight` picks the matching Plus Jakarta Sans face and is then dropped (keeping it would ask the OS to synthesise bold on top of a face that is already bold); otherwise it is body text, Plus Jakarta Sans Regular. A `Text` nested inside another with no family/weight of its own is left alone so it keeps inheriting the parent's face.

Type scale (`typeScale` in `theme.ts`) — use these, don't hand-pick `fontSize`. Every token names its font family. Eight text tokens and three numeric readouts replace the 16 distinct literal sizes (10–30px) the app had drifted into:

| Token            | Font          | Size                         | Use                                                                                                 |
| ---------------- | ------------- | ---------------------------- | --------------------------------------------------------------------------------------------------- |
| `display`        | displayHeavy  | 32                           | Rare hero/large-heading moment (e.g. a completion screen) — not a general `screenTitle` replacement |
| `screenTitle`    | displayHeavy  | 24                           | Standard screen title (`AppHeader`'s `title`)                                                       |
| `sectionHeading` | display       | 12, uppercase, letter-spaced | `SectionHeader` labels                                                                              |
| `cardTitle`      | display       | 16                           | Card/row titles, `ErrorState` title                                                                 |
| `statLarge`      | monoBold      | 30                           | `StatValue`/`Stat` large                                                                            |
| `statMedium`     | mono          | 19                           | `StatValue`/`Stat` medium                                                                           |
| `statSmall`      | monoBold      | 15                           | `Stat` small, a `ListRow`'s trailing value                                                          |
| `body`           | body          | 15                           | Standard body text, input text                                                                      |

## 6. Spacing

```
xs: 4   sm: 8   md: 12   lg: 16   xl: 20   xxl: 24   xxxl: 32
```

`spacing.xxl` is the standard screen horizontal padding (`Screen`, `AppHeader`, `BottomSheet`). Always reference `spacing.*` — no raw pixel margins/padding for values this scale already covers.

**`widgetGap` (6)** — a separate token exported from `theme.ts`, deliberately _not_ a step on the scale above. It is the **maximum** gap between two adjacent widgets (cards, stat blocks, and the rows of blocks that hold them) on any of the app's widget-stack screens -- Feed, Train, Nutrition, and the card-based Profile/Progress (§17). It is applied once, as `gap` on each widget stack's `contentContainerStyle` — individual widgets carry no outer margin of their own, and a stack never distributes leftover viewport height between its widgets (no `justifyContent: 'space-between'`, no `flexGrow` spreading) nor squeezes them to fit a fixed height. It governs only widget-to-widget separation; a card's internal padding, header spacing and text spacing still use `spacing.*`.

**`minTouchTarget` (44)** — also exported from `theme.ts`: the smallest comfortable touch target. Controls are at least this size, either visibly or through `hitSlop` (§19).

## 7. Border Radii

```
sm: 8   md: 12   lg: 16   pill: 999
```

Each radius has one role, so nested surfaces stay optically concentric (the outer radius is at least the inner radius plus the gap between them):

- `sm` — small inset elements (a wheel-picker highlight, a progress-bar track)
- `md` — **controls**: buttons, inputs, chips, icon wells
- `lg` — **surfaces that contain controls**: cards, bottom-sheet top corners
- `pill` — fully-rounded: segmented controls, badges, tab pills, the bottom-nav's center "+" button, avatar circles

(Controls used to sit _above_ their card — buttons 14 vs cards 10 — which reads as inverted once a button is inside a card.)

## 8. Buttons (`apps/mobile/src/design/Button.tsx`)

Four variants, three sizes, one file, no others. All four share one implementation of the pressable frame, sizing, disabled/loading rules and accessibility contract (role `button`, name = label unless `accessibilityLabel` overrides it, `{ disabled, busy }` state):

- **`PrimaryButton`** — filled, `radii.md`, accepts `accentColor`/`onAccentColor` (default `colors.accent`/`colors.onAccent`) so it can follow a screen's mode theme (mirrors `SegmentedControl`/`Toggle`'s override pattern). Background/text color are always supplied inline from these props — never hardcoded in the stylesheet, so there's no stale default to fall out of sync.
- **`SecondaryButton`** — outlined (`colors.border`), `textPrimary` label.
- Any of the three framed buttons can carry an optional Feather `icon` before its label, in the label's colour (Nutrition Today's Log Food, Scan Barcode and Search Food). The label still names the button.
- **`DestructiveButton`** — outlined in `destructiveBorder`, `destructive`-colored label. For destructive actions only.
- **`TextButton`** — plain text link, `textSecondary`, no container, but a full 44pt tall target.

**Sizes** (`size` prop): `lg` (default, 52pt — the full-width primary action), `md` (44pt — a standard inline action), `sm` (36pt visible with an extended touch area so the target is still 44pt — compact contexts).

**`loading`** replaces the label with a spinner (in the label's own colour), blocks presses and reports `busy` — the one place a "saving…" state lives, instead of each screen hand-rolling its own.

`disabled` → `opacity: 0.5` (the app-wide disabled convention, §16). No fifth variant should be introduced without updating this file.

## 9. Inputs (`apps/mobile/src/design/TextInput.tsx`)

One bordered row: optional `label` above, the input itself (with optional left/right accessory slots), optional `error`/`helperText` below. Border color is a single computed value from three states — `error` → `destructive`, `focused` → `textSecondary`, default → `border` — never separate style objects per state to keep in sync. `error` presence always wins over `helperText`. Placeholder text uses `colors.textMuted`.

## 10. Cards (`apps/mobile/src/design/AppCard.tsx`)

**In-progress redesign note:** FeedScreen and WorkoutHistoryScreen have moved to a new, separate `Card` component (`apps/mobile/src/design/Card.tsx`) — a flat surface (`colors.surfaceRaised` at `widgetFillAlpha`, 80%, so the background photo shows through it; no glass layer, no blur) with a bigger `radii.xl` corner and a faint warm hairline edge (`colors.glassBorder`, drawn as an absolutely positioned overlay so it never changes the card's size or padding). `Card` has no `topAccent`/`outline`/`variant` — regular cards stay neutral, and the _one_ hero card on a screen (Feed's Next Workout, Workout History's start/resume action) is `hero`: no fill and no edge, so its content sits straight on the background photo (§3a), as in the Warm Minimal reference, with full `textPrimary` text (never a faded tint — it sits straight on the photo, which Feed brightens behind its hero, §3a) and a `colors.heroAction` cream button with `onAccent` text. Every other screen is unchanged and still uses `AppCard`/`GlassBackground` exactly as documented below; this section describes that still-current system, not the redesigned screens' new one.

Use a card where it **earns its place**: something the user taps, or a set of facts that genuinely belong together. Do not make it the default wrapper for every block of content — a screen of floating rectangles is exactly what this system avoids. Default to sections and rows (§17).

One card component, two variants plus the rare hero. The default is a glass surface (§3b — `GlassBackground`'s `surface` variant, tint + hairline border, no blur):

- **`variant="surface"`** (default) — translucent tint of `colors.surface`, `glassBorder` hairline, `radii.lg`, `spacing.lg` padding.
- **`variant="outline"`** — the same frame with no fill, only the `glassBorder` hairline: for grouped content that shouldn't read as a raised, floating object.
- **`hero`** — same treatment as `surface`, tinted toward `surfaceHero`/bordered in `borderHero` (§4) instead of `surface`, so it still reads as "the important one." Reserved for one card per screen.
- **`topAccent`** — an optional slim (3px) band across the card's top edge, clipped to the card's own corners. The one Strava-style flourish this system borrows (see §17's Feed section): a quick, glanceable "what kind of activity is this" cue. On Train/Nutrition/Profile it carries the accent (the one soft amber); on Feed specifically it is always the fixed neutral `colors.textPrimary` regardless of any custom accent, so its cards tell a workout from a food log by byline icon, never by colour. Most cards have none; reach for it on a card that represents one real, completed piece of activity (a workout, a logged meal), not as general decoration.

**A card never contains another card.** `AppCard` tracks nesting and warns once in development if one is rendered inside another (it never changes rendering, and is silent under test/production). Group with spacing, a hairline or a `ListRow` instead. The card's radius (`lg`) sits above the control radius (`md`), so a button or input inside a card stays optically concentric.

`AppCard` renders as a `TouchableOpacity` when given `onPress`, otherwise a plain `View` — never wrap it in an extra pressable yourself.

An earlier readability pass gave Dashboard's Workout/Nutrition cards their own extra `darkCardTint` layer merged into `AppCard`'s outer `style`, on top of `GlassBackground`'s own tint — a scoped, per-screen darkening because `surface`'s tint alone (60% at the time) wasn't separating content from those photo backgrounds clearly enough. That default has since been raised app-wide instead (see §3b), which fully supersedes the one-off: `darkCardTint` has been removed, and every `AppCard` everywhere (not just Dashboard) now gets that same strong foundation from the one shared token, per the "modify the shared component, not each screen" rule this system is built on.

Nutrition mode has no foreground layer: its widgets fill the screen down to the bottom navigation (§17), over the same background as every screen (§3a).

## 11. Navigation

Three distinct, non-overlapping navigation surfaces — don't conflate them:

1. **`BottomNavBar`** — the **one** bottom navigation in the app, and the app's sole means of moving between Train and Nutrition content now (there is no Workout/Nutrition toggle — see point 4). Five fixed tabs, always the same label and icon regardless of where you currently are: **Feed** (the landing screen — a personal activity feed, §17), **Workouts** (the Train section — Workout History and its pages; labelled Workouts, internally still `train`), **Nutrition**, **Progress**, **You**. Mounted once in `App.tsx` as an in-flow sibling of the navigator, so it persists across every push/pop and appears on every screen, Feed included — there is no second, screen-owned copy anywhere. Hidden only on Onboarding and the pre-sign-in screens (which render outside the navigator). A glass `chrome` surface (§3b — real blur + `glassBorderStrong` top edge only, no side/bottom border since it's flush with the screen edges). Each tab is at least 56×48pt, an accessible `tab` named by its label (§19). Train and Nutrition each carry their own fixed accent (the theme's accent -- soft amber in the default; there is no free colour picking) whenever active, regardless of which tab you came from; the mode-agnostic tabs (Feed, Progress, You) use whichever of the two the user was most recently in (`neutralAccentColor`, sourced from `App.tsx`'s `sharedMode`). Inactive tabs use `textSecondary`. Progress shows its own "Nutrition progress is coming soon" state when `sharedMode` is Nutrition, since it has no Nutrition-side content yet. **In the Trainer Workspace** (`trainerTabs`) the five become that workspace's three, in the same style: **Clients** (`users` -- the workspace's home), **Activity** (`activity` -- every client's latest workouts) and **Sessions** (`clock` -- live sessions and logging for a client); each trainer page keeps its tab highlighted (`routeToBottomNavTab`: a client's page, the add/edit form and claim codes under Clients; logging and a live session under Sessions). The bar's top edge is then a thin line of the accent instead of `glassBorderStrong` -- with the different tabs and the workspace pill, it's how a glance says which workspace you're in. None of the three leads back to My Workspace; only the switcher does.
2. **`AppSideMenu`** — the app-level global drawer (hamburger → full destination list, grouped under `SectionHeader`s), animated via `Animated`/`Pressable` (no drawer-navigator dependency), 280px wide, slides from the left, dismissible via backdrop tap or Android back button. Also a glass `chrome` surface (blur + `glassBorderStrong` right edge only) — the backdrop behind it stays the existing opaque `rgba(0,0,0,0.6)` scrim. Its two section lists (`APP_MENU_SECTIONS`, `apps/mobile/src/navigation/appMenuSections.ts`, and `NUTRITION_MENU_SECTIONS`, `nutritionMenuSections.ts`) are strictly mode-scoped — the Workout menu never lists a Nutrition destination and vice versa; Feed and You aren't in either (each is already one tap away via the bottom nav). The hamburger itself is reachable the same way from every Train/Nutrition/Progress screen that's a bottom-nav/side-menu destination in its own right — Feed, Workout History, Progress, Workout Splits, Exercise Library, Nutrition Today, and Food Library/Nutrition Goals all open it from their own header (replacing what would otherwise be a back button, since none of these are deep task screens). You (Profile) is the one exception: it has no hamburger, since its header's Settings action already covers its one onward destination. Screens reached by pushing forward from one of those (a workout's detail, an active session, starting a new workout, Food Search, etc.) keep a plain back arrow instead.
   **Workspace switcher (trainers only)** (`workspace/WorkspaceSwitcher.tsx`, `workspace/WorkspaceContext.tsx`): a trainer has two workspaces -- **My Workspace** (Personal: the whole app as everyone has it) and **Trainer Workspace** (Clients & Coaching). A pill in the title's place on Feed and on each of the Trainer Workspace's three tab pages -- Clients, Activity, Sessions (`AppHeader`'s `titleContent`) shows the one you're in -- your picture (or, for the trainer workspace, an amber group glyph), its name and kind, a chevron -- and drops a **Switch Workspace** panel down from the top of the screen (chrome glass, rounded bottom corners, a grabber at its foot, a dimmed backdrop; 260ms, instant under Reduce Motion) offering just those two as option cards: the current one bordered and tinted in the accent with an amber check, the other with an empty radio. No other workspaces and no workspace settings. Picking the trainer workspace opens the trainer's **Clients** page (its home, a section page with the menu button), swaps the bottom nav for the workspace's own three tabs (point 1) and the side menu for the trainer menu (`TRAINER_MENU_SECTIONS`: Clients, Activity, Sessions, Add Client); picking My Workspace returns to Feed, the five tabs and the personal menu. Anyone who isn't a trainer never sees the pill -- Feed keeps its Progresso title.
3. **`UnderlineTabs`** (`apps/mobile/src/design/UnderlineTabs.tsx`) — a screen-local horizontal tab row for a screen's own internal sections: for a small, fixed group that should always all be visible at once, evenly dividing the full row rather than scrolling — icon stacked above label, the active tab marked by a colored underline rather than a filled pill (the exact Strava tab treatment, by explicit request). Used by Profile's Workouts/Stats/PRs switcher and Progress's Overview/Top Sets/Nutrition/All Time switcher (§17's You/Profile and Progress bullets). Its horizontally-scrolling pill-tab sibling, `CategoryTabs`, was retired along with Settings' old in-screen-tabs layout (§17's Settings bullet) — nothing in the app needs a scrolling tab row any more, so don't reintroduce one without the same justification that would apply to any other new component.
4. **No Workout/Nutrition toggle.** Moving between Train and Nutrition content is exclusively the bottom nav's job now (point 1) — there is no in-page segmented switch anywhere, and no bottom-nav center "+" (the former `ModeToggle` component is gone, and it stays gone). `App.tsx`'s `sharedMode` flag — what the mode-agnostic roots (Feed, Progress, You) and `AppSideMenu`'s default fall back to when a screen has no mode identity of its own (see `isNutritionRoute`/`MODE_AGNOSTIC_ROUTES`) — updates itself automatically: landing on any route with an unambiguous mode sets it, so the fallback always reflects wherever the user was a moment ago, with nothing to explicitly report. Feed's own header carries one scoped exception: a "+" (mirroring Strava's top-bar button, §17) that opens a small `BottomSheet` shortcut straight to Start Workout / Log Food — a faster path from Feed, not a replacement for Train's/Nutrition's own primary buttons, which remain the normal way in.

**Screen transitions** (`apps/mobile/src/navigation/navigationTransitions.ts`, applied once at the navigator level in `App.tsx` from each route's name — a new screen gets one with no setup): a page's transition says what kind of move opening it is, so the app uses three, never a one-off per screen:

- **Sections switch instantly** (`animation: 'none'`) — the bottom nav's five tabs and the side menu's section pages (Workout Splits, Exercise Library, Food Library, Nutrition Goals, Nutrition History, Calorie Estimation, Log a Past Workout, Trainer Access) and the Trainer Workspace's three tabs (Clients, Activity, Sessions), i.e. every page with the menu button rather than a back arrow. They're peers, not deeper, so a slide would mislead; this matches iOS's own tab bars. A tab tap, or a side-menu section, **goes to** that section rather than stacking another copy of it (`goToSection`, `navigation/sectionNavigation.ts`): from another section the history becomes just that section; already in it, it pops back to the section's first page, like tapping the current tab on iPhone. So the history never piles up -- swiping back from a section doesn't return to the previous one, as in any tab app, while back from a deeper page still returns through its section. Pages that aren't in view are frozen (`freezeOnBlur`) and stop re-rendering until they are again.
- **Deeper pages slide in** with the platform's own native push (`animation: 'default'` — iOS's slide with parallax) — every page with a back arrow. A `replace` into one (Start → the live workout, a saved past workout → its detail) slides forward like a push too (`animationTypeForReplace: 'push'`).
- **Short tasks slide up from the bottom** (`slide_from_bottom`, 350ms) — a tool you open, use and close to land back where you were: Barcode Scanner, Food Search, Share Workout, Choose Your Split. Like the app's other pop-ups (`ExercisePickerModal`, `BottomSheet`), their header's left button is a close **`x`** ("Close"), not a back arrow; a step back _within_ the task (e.g. Food Search's selected food → its results) keeps the arrow.

Swipe-back stays on everywhere (`gestureEnabled` + `fullScreenGestureEnabled`). On a task page the swipe is **downward** and only starts in the top `TASK_SWIPE_BAND` (150pt — the status bar and header): a full-screen vertical swipe would claim the drag before a list underneath could scroll. Respects Reduce Motion (`useReduceMotionPreference`): every page switches instantly — any new animated component should check this same hook rather than adding a second reduced-motion mechanism (see `AppSideMenu`, `BottomSheet`).

## 12. Tabs / Segmented Controls

- **`SegmentedControl`** (`apps/mobile/src/design/SegmentedControl.tsx`) — a pill-shaped row of equal-weight segments (e.g. kg/lb, cm/ft-in) on a glass `surface` track (§3b — tint + hairline border, no blur). Selected segment gets an `accentColor` fill (default brand accent, solid, not glass); selection changes **color only** — never size, weight, padding, or border, so a selected segment never grows relative to its unselected size.
- **`ChoiceTile`** (`apps/mobile/src/design/ChoiceTile.tsx`) — a raised tile (`surfaceLift`, `glassBorder` hairline, `radii.md`, `spacing.md` padding) that is either one choice of a set (`selected`: Nutrition Goals' four estimates, Personal Information's Male / Female) or opens a picker (no `selected`: a height, a weight, a birthday, an activity level). Chosen, an accent edge and a 14% accent tint fade in over it (180ms) and a small filled check appears in its top-right corner, with a spring "pop" from 94%; pressed, any tile gives to 96%. Every motion is on the native driver, and under Reduce Motion it simply changes. It's a `button` named by its own label, reporting `{ selected }` only when it's a choice. Two side by side are `widgetGap` apart, like `StatBlock`s. Use it where a choice deserves a picture or a figure of its own; a plain either/or (kg/lb) stays a `SegmentedControl`.
- **`UnderlineTabs`** — see §11. A colored bottom border plus icon/label color marks the active tab, not a filled pill — this is Strava's own tab treatment, reproduced deliberately.
- **Known layout trap, already fixed once, do not reintroduce it:** a horizontal tabs `ScrollView` sitting above a vertical content `ScrollView` will fight it for leftover space unless the tabs' `ScrollView` has explicit `flexGrow: 0` and its row has `alignItems: 'center'` (a flex row's cross-axis defaults to `stretch`, which stretches pills to whatever height the row ends up with). Nothing uses a scrolling tab row now (`CategoryTabs` was retired with Settings' old tabs, §11), so this only matters if one is ever reintroduced.

## 13. Badges (`apps/mobile/src/design/Badge.tsx`)

One badge style. Default: brand-accent text on a 14%-alpha accent-tinted pill background. Accepts optional `color`/`backgroundColor` overrides for a screen with its own accent theme (e.g. a Nutrition-mode screen's green) — every other caller is unaffected. Used for: PR/achievement labels, and the "Coming Soon" state (`ComingSoonRow`, muted gray variant: `textMuted` on `surfaceRaised`). There is no separate "success" badge color (§4).

## 14. Icons

**Feather (`@expo/vector-icons`) exclusively.** No other icon set is used anywhere in the app. Standard sizes: 16 (inline row icons), 18 (header/menu actions), 20 (bottom-nav items), 22 (center "+" button). Icon color follows context: `textMuted` at rest, `textSecondary`/`textPrimary` for emphasis, the active accent when representing an active/selected state.

`IconButton`'s default (bordered-circle) state is a glass `surface` (§3b, no blur) — this is what carries the new visual language into every header's back/settings/action buttons without touching `AppHeader` itself. Its accent-filled state (`backgroundColor` prop passed — an accent-driven action) stays a solid, opaque fill, same reasoning as buttons in §8.

## 15. Modals / Bottom Sheets

- **`BottomSheet`** (`apps/mobile/src/design/BottomSheet.tsx`) — the generic primitive: `Modal` + semi-transparent (`rgba(0,0,0,0.5)`) backdrop `Pressable` + a glass `chrome` sheet (§3b — blur + `glassBorderStrong` top edge) with only the top corners rounded (`radii.lg`), sliding up from the bottom. Respects Reduce Motion (`animationType: 'none'` vs `'slide'`). Backdrop-tap-to-dismiss is on by default (`dismissOnBackdropPress`).
- Any new bottom-sheet-style UI should use `BottomSheet` directly rather than hand-rolling the Modal/backdrop/sheet structure again.

## 16. States

- **Loading**: never a blank page and a spinner. `LoadingState` is the page's shape -- a header bar and card-shaped `Skeleton`s (`SkeletonCards`) that gently pulse (static blocks under Reduce Motion) -- on the transparent page, so the background shows; `inline` drops the header bar for a screen already showing its own. Within a page, use `SkeletonCards` for a stack of cards and `SkeletonRows` for a `ListRow` group (`design/Skeleton.tsx`), each with the testID the spinner it replaced had. A spinner is only ever for an action under way -- a button's own, a photo saving, one part of a review being looked up -- never for a page's or a list's content (search results, the Food Library, the exercise library, Find People, notifications, a workout's or a record's detail all load as skeletons). **Reopened pages start from what they last showed:** a section page is opened fresh on every section switch (§ Screen transitions), so Feed, Workout History and You remember what they last showed this session (`lib/lastShown.ts` -- in memory, per user, forgotten on sign-out) and show it at once while they refresh in the background; only the very first load shows placeholders. **Charts wait for their page to arrive:** a pushed page is drawn before its slide-in starts, so `LineChart` (and with it every `WeeklyTrendChart`), `ProgressionChart` and `CalorieRing`'s ring draw a same-size `Skeleton` until the page has arrived (`PageArrival`/`usePageArrived` in `navigation/useAfterTransition.tsx`, wrapped around every page by App.tsx's `screenLayout`; 600ms fallback) -- the slide starts the moment you tap, and anything mounted later on an arrived page (a tab switched to) draws at once. Inline/header-level loading (e.g. a save in progress) keeps a small `ActivityIndicator` in place of the action icon (`AppHeader`'s `loading` prop, `IconButton`'s `loading` prop) or a `Button`'s own `loading` prop.
- **Empty**: `EmptyState` — optional icon slot + centered muted title (`textMuted`), an optional one-sentence `description`, and an optional single `action` (a small `SecondaryButton`) for the obvious next step. Replaces ad hoc "no data" gray text.
- **Error**: `ErrorState` — icon slot + `cardTitle`-styled heading ("Something went wrong" by default) + muted message + optional plain-text "Retry" action (not a filled button — retrying isn't a destructive action, so it stays visually calm).
- **The app failing outright**: `AppFailure` (`src/AppFailure.tsx`) — shown instead of a blank screen when the app's code fails to load (`index.ts`) or a screen throws while drawing (`AppErrorBoundary`). Deliberately plain, since it may show before fonts load or anything else works: `colors.background`, "Progresso hit a problem" in a heavy 24pt system face, a `textSecondary` line saying what to do, the error's own message in a `surfaceRaised` box (`radii.md`, monospaced, selectable so it can be sent), and — only after a screen failed — a `heroAction` **Try Again** pill. It never replaces `ErrorState` for an ordinary failed load.
- **Disabled**: `opacity: 0.5`, uniformly, across every interactive component (`Button`, `TextInput`'s row, `SegmentedControl`, `Toggle` via native `Switch`, `IconButton`). Don't invent a second disabled treatment.
- **"Coming Soon" (visible-but-not-yet-functional)**: `ComingSoonRow` — a real row with a muted "Coming Soon" `Badge`, never a toggle or button that silently does nothing when pressed. Use this pattern whenever UI is intentionally ahead of its backend.

## 17. Layout Principles

- **`Screen`** (`design/Screen.tsx`) is the one screen frame: a transparent root (so `AppBackgroundLayer` shows through — a screen never paints its own background), the device's real top safe-area inset when there is no header (an `AppHeader` pads for it itself), an optional header slot, a scrolling or static body, 0 horizontal padding, and opt-in keyboard avoidance. It reserves no space for the bottom navigation — `BottomNavBar` is an in-flow sibling of the navigator, so the content area already ends above it. `ScreenContainer` predates it and remains only for the launch screen.
  - **Edge-to-edge widgets, no screen-edge gutter.** 0, not `spacing.xxl` (24px) or an intermediate `spacing.sm` (8px) tried first — every widget runs flush to the screen's own left/right edge, by explicit request, no gap at all. Any screen that manages its own gutter in parallel (via `Screen`'s `padded={false}` -- Progress, Food Library, New Workout's empty state) uses the same 0 value for consistency. A widget's own internal content padding (`AppCard`'s `spacing.lg`, §10) is unrelated and unchanged -- this is only the outer gutter between a widget and the screen edge. `AppHeader` does **not** match this: its title text and icons (Back, the hamburger/side menu, a '+') read as cramped flush against the edge, so it keeps its own standard `spacing.xxl` screen gutter instead (§6) -- only the widget stack below it is edge-to-edge.
- **Every page is widgets.** A page's content sits in widgets -- `Card`s -- on the background, like Feed, Train and You. `Section` (`design/Section.tsx`: a `SectionHeader` plus an optional quiet header action) is itself a widget when it stands on its own on a page: a `Card` with its heading inside, so a page built from Sections (Settings, the forms) reads as widgets. Inside a card already it is just a titled group -- never a card in a card (`design/insideCard.ts`: `Card` and `AppCard` tell their contents they're inside a card). Pages with no Sections wrap their own groups in `Card`s (e.g. Progress exercise detail: current best, chart, Best Performances, Progression Journey). The live workout is widgets too: the workout's own (pinned) and one per exercise (see Live workout below). Do not nest section headers.
- **`ListRow`** (`design/ListRow.tsx`) is the one list-row pattern, generalised from the Settings row: an optional 36pt neutral icon well, a title and optional subtitle, and a trailing chevron, mono value or custom control, with an optional hairline `divider` above. A group of rows on the screen replaces "a card per item" for history entries, exercises, meals, splits and settings alike.
- **`Stat`** (`design/Stat.tsx`) is the labelled numeric readout (a mono `StatValue` plus a quiet caption). It is neutral by default — accent-colour only the one number that matters most — and it is never a card of its own.
- **Feed composition** (`screens/FeedScreen.tsx`, replacing the old Dashboard). The app's landing screen: a personal activity feed -- there is no following/social graph, so this is "what did I actually do", never anyone else's data. One data source per item kind (`feed/feedQueries.ts`): the user's own completed workouts (paginated, oldest reachable via **Load More**) and this week's logged foods, merged into a single reverse-chronological stack of the redesign's flat `Card`s (§10's redesign note), `widgetGap` apart. Each card's anatomy borrows Strava's activity-card structure -- a byline row, a bold title, a stat strip -- but Feed's regular cards are **neutral** (Warm Minimal), a deliberate call over adopting Strava's orange: a regular card carries no colored band at all (flat, neutral `colors.surfaceRaised` with a faint warm edge), and announces what kind it is with a small icon in its byline (an activity glyph for a workout, a coffee-cup glyph for a food log), never a colour. The one exception is the Next Workout hero, a photo `hero` Card (§10) -- the warm gym photo with off-white text and a cream Start Workout button, the single bold moment on the screen, not a band on every card. While a workout is going, the same hero (`feed/FeedHeroCard.tsx`, shared by both) shows it instead -- "Workout in Progress", its name, "Your workout · started 6:42 PM" and a cream **Resume Workout** -- not a widget; any other open workout (a group, a trainer session) is a quiet Live now card under it. Feed knows a workout is going the moment the live workout opens (`feed/liveWorkoutMemory.ts`), so it never shows "start your next workout" first, and it doesn't offer the next workout until it knows none is going. The byline row is an avatar (`Avatar` -- initial/photo fallback) plus the signed-in user's own name, from the same profile fetch `useProgressTheme` already makes (no second request). Two things Strava's reference screen has that Feed deliberately does not attempt: a GPS route map (Progresso has no location data anywhere in its model -- there is nothing real to draw) and a streak/"congratulate" banner (a social prompt, and Feed stays purely informational with no kudos/social elements since there's no social graph -- following/kudos is a real, separate future feature, not a reskin, and needs its own plan before it's built). Every workout card -- the signed-in user’s own and accepted followees’ alike -- shows its stat area as a single row of three `StatBlock`s: Duration, Exercises (exercises with at least one completed set), and Sets. There is no Volume on the card. Beneath it sits a **Top Sets** strip (`feed/RecentWorkoutTopSets.tsx`): one slide per exercise whose heaviest completed set is its top set (`workouts/recentWorkoutTopSets.ts`, built on the same `heaviestSet` definition as WorkoutDetail), swipeable, auto-advancing every 3.5s (held while dragging, not animated under Reduce Motion), with pagination dots. When an exercise has a machine photo (`exercises.photo_url`), its slide shows that photo as an `ExercisePhoto` circle (56pt) beside the name and readout, and tapping it opens the full-size image in `PhotoLightbox`; an exercise with no photo gets no placeholder and no reserved space. This applies identically to the signed-in user's own cards and to followees' cards, where the photo URL comes from the backend friends feed. `exerciseCount` rides along on `enrichWorkoutSummaries`' existing `workout_exercises` fetch, no extra query. A food card leads with a hero-sized picture (`FoodImage` at 88pt, matching `FoodFacts.tsx`'s own "found a food" sizing -- §17's Nutrition section) beside its name and a large neutral `StatValue` calorie readout, then Protein/Carbs/Fat as three more `StatBlock`s -- all three macros, not just Protein. Tapping a card opens that workout's detail or Nutrition Today. A followee's workout card ends its byline with a bare "more" glyph (`more-horizontal` in muted text, a full 44pt target, the same bare-glyph treatment as the live workout's reorder/remove) that opens `PersonActionsSheet` (`social/PersonActionsSheet.tsx`); your own cards have none. That sheet -- also opened by tapping a person in Find People -- is a `BottomSheet` with a mini profile (avatar, name, @username) above two `ListRow`s: Report (the person, or "Report Workout" from a card) and Block as a destructive row, which confirms with an alert. Reporting swaps the rows for a reason list (one `ListRow` per reason, the picked one marked with an accent check), an optional details `TextInput` and one filled Send Report, then a thank-you with Block still offered and one filled Done. A blocked person leaves the screen at once. The header's right action is a "+" (§11, point 4) opening a `BottomSheet` shortcut straight to Start Workout / Log Food. Loading/error/empty states use the shared `LoadingState`/`ErrorState`/`EmptyState` exactly like any other screen -- nothing here is a special case.
- **Feed's Steps card** (`feed/StepsCard.tsx`, iPhone only). Under the hero (Next Workout or the workout going), above the activity cards: a regular neutral `Card` whose heading row is a muted `trending-up` glyph, "Steps Today" in `label` and a muted "Apple Health" caption on the right. Connected, the count is a large neutral `StatValue` (`textPrimary`, like Feed's other figures); a count of 0 adds one `secondary` line saying where in the Health app to allow it, since Apple Health never tells an app it was refused. Until Progresso has asked, the card says what it would show and that steps stay on the phone, with one `SecondaryButton` (`md`, heart glyph) **Connect Apple Health**. If Apple Health can't be reached at all, the card says so in a `secondary` line with the error beneath it in a muted `caption`, instead of disappearing. Absent off iPhone or where Health isn't available -- never a disabled card.
- **Home Screen widgets and the Lock Screen card** (`widgets/homeWidgets.ios.tsx`, iPhone only). Drawn in SwiftUI by the widget extension, not React Native, so they follow the app's tokens by value: `colors.background` fill, `textPrimary` figures and titles, `textSecondary` captions and labels, the amber `accent` for the small heading glyph, eyebrows and progress bars, and Next Workout's action as a `heroAction` capsule with `onAccent` text -- the Feed hero's cream button. The app's fonts aren't in the extension, so text is the system face, with figures in its monospaced design (the app's mono readouts) and titles heavy. **Today's Nutrition**: "Today" with a fork-and-knife glyph, calories left (or over, or eaten without a target) large, the caption, and a bar; the wide size adds Protein / Carbs / Fat rows, each "eaten / target g" with its bar. **Next Workout**: an amber eyebrow (Next Workout or Workout in Progress), the day or workout name, the muscles or "started 6:42 PM", and Start / Resume / Open. **Today's Steps**: "Steps" with a walking glyph, the count large, "As of 3:42 PM" -- a dash when it isn't known for the day. **Lock Screen card** (a Live Activity): an amber dumbbell glyph, the workout's name over "Your workout" / "Group workout", and a running amber timer on the right; in the Dynamic Island, the glyph and the timer. Before the app has handed a widget anything, or once signed out, it says to open (or sign in to) Progresso -- never an empty or made-up figure.

- **Widget pages.** Beyond Feed, every screen that holds several distinct groups -- across Train, Nutrition, and (see below) Progress/You -- is a stack of widgets: `Screen`'s scrolling body with `gap: widgetGap` (6px) between `AppCard`s, the same rhythm as the dashboards. A widget is one group -- a summary, a calendar, an exercise, a list -- with its own `SectionHeader` when it needs one; rows inside it are `ListRow`s separated by hairlines and stats inside it are `StatBlock`s (`design/StatBlock.tsx`: a quiet raised block, the figure in the mono face, its label beneath; blocks are `widgetGap` apart; not a card, so it never nests one). - **Signed-out and onboarding (Phase 6).** Sign In, Sign Up, Forgot / Reset Password and Welcome share one frame, `AuthFrame` (the shared `Screen` with keyboard avoidance, a title and optional mark, and a short fade-in that respects Reduce Motion and is cancelled on unmount). ## 18. Responsive Behavior

The app is phone-only (no tablet-specific layout exists). Within that: `WheelPicker` and similar fixed-height components use device-independent point values, not percentage-of-screen math, since none of today's screens need to adapt beyond standard phone widths. When a layout must respond to content length rather than screen size (e.g. tabs vs. content competing for space), see the flex trap documented in §12.

## 19. Accessibility & Contrast

- Every interactive element sets `accessibilityRole` (`"button"`, `"switch"`) and a meaningful `accessibilityLabel` — icon-only controls (`IconButton`, `AppHeader` actions) always require an explicit label since there's no visible text to fall back on.
- `accessibilityState` reflects real state: `{ selected }` for tabs/segments/menu items, `{ disabled }` for anything that can be disabled, `{ checked }` for `Toggle`.
- Accent colors are contrast-checked, not assumed: `buildAccentTheme` computes WCAG relative luminance/contrast against both ink colors and picks whichever wins (§3) — this is the one place in the app doing real contrast math, and any new accent-driven text-on-fill combination should reuse it rather than guessing. Text straight on the background photo relies on the photo's measured darkening (§3a).
- Reduce Motion is respected everywhere an animation exists (`AppSideMenu`, `BottomSheet`, screen transitions) — a new animated component must check `useReduceMotionPreference()` too. `AppBackgroundLayer`'s depth overlay (§3a) is a static gradient, never animated, so it needs no such check.
- Widgets are translucent, not indistinct: the shared widget fill opacity (`widgetFillAlpha`, 80% — `Card` and `GlassBackground`'s `surface`; `chrome` is 80% plus blur) was measured over the sunset photo's brightest pixels, Feed's brighter hero state and scrolling included, so `textPrimary` and `textSecondary` keep WCAG AA inside a card, a `surfaceLift` block included. A raised block inside a widget uses `surfaceLift`, never an opaque `surfaceRaised` patch, so it doesn't block the photo the card lets through. Never reduce a widget's fill opacity, or raise `surfaceLift`, without re-measuring text contrast on top of it — the background must never overpower foreground content.
- **Touch targets are at least 44pt** (`minTouchTarget` in `theme.ts`). `Button` sizes, `ListRow`, `SegmentedControl` segments, `ErrorState`'s retry and every bottom-nav tab meet it visibly; `IconButton` (36pt visible), the compact `sm` button and `Section`'s header action keep their small appearance and extend the touch area with `hitSlop`.
- The bottom navigation is exposed as a `tablist` of `tab`s, each named by its visible label, with `{ selected }` state; a `Button` reports `{ disabled, busy }` and is named by its label unless overridden; `SkeletonRows` announces a single "Loading" state rather than one stop per block.
- Text scales with the user's Dynamic Type setting, so no screen may depend on a fixed height (§20). Dashboard's Nutrition mode was the last fixed-height, non-scrolling layout and now scrolls, exactly like Workout mode, so larger text can never clip a widget.

## 20. UI Do's and Don'ts

**Do:**

- Reference `colors`/`spacing`/`radii`/`typeScale`/`fonts` from `theme.ts` for every value those scales cover.
- Reuse an existing component (`AppCard`, `Badge`, `SegmentedControl`, etc.) before writing a new one; if a genuinely new pattern is needed, add it to `apps/mobile/src/design/` so it's shared, not screen-local.
- Let mode-aware components (`PrimaryButton`, `SegmentedControl`, `Toggle`, `Badge`, `BottomNavBar`, `MuscleVisualization`) receive `accentColor`/`onAccentColor` from the caller rather than hardcoding a color inside them.
- Reuse `GlassBackground` (§3b) for any new "major surface" (a card, a persistent chrome bar, a modal) instead of hand-rolling translucency/blur — render it as the surface's first child and keep the consumer's own border-radius/`overflow: 'hidden'`.
- Use `ComingSoonRow` for real-but-not-yet-functional UI instead of a control that does nothing.
- Check `useReduceMotionPreference()` before adding any new animation.
- **Widgets roll out on every page** (`RiseIn`/`RiseInGroup`/`RiseInStack`, `design/RiseIn.tsx`): when a page opens, its widgets spring up from 44pt below, growing from 94% to full size and fading in, settling with a slight bounce (a soft spring, about half a second; 110ms apart, only the first six waiting their turn; native driver), top to bottom, instead of popping in at once. `Screen` does this for every page (`rollout`, default true): `RiseInStack` gives each direct child its own `RiseIn` in one cascade (a fragment's children each take their own turn), adds no box of its own, copies how each widget sits in the page onto its wrapper (`flex`/`flexGrow`/`flexShrink`/`flexBasis`/`alignSelf`; scrolling lists fill by default), and never wraps anything pinned in place (`position: 'absolute'`), so no page's layout changes. Pages opt out where they roll out their own: Feed (live cards, the Next Workout hero, then each workout card), Progress (its tabs, then the section card filling the screen -- its content follows a frame later, with skeleton blocks for that frame, so tapping the tab never waits on it), the Exercise Library (its browser's two cards, via `RiseInStack` inside `ExerciseBrowser`), and the live workout, Edit Workout, Log a Past Workout and group and trainer sessions (each widget in their scrolling list, via `RiseInStack` inside it -- never the list as a whole too, which would double the motion). A pinned footer doesn't roll out. Onboarding keeps its own step frame. Widgets appearing within 250ms of each other cascade together, whether from what a page last showed or freshly loaded; one that appears later on its own (a new workout after a refresh, the next page at the bottom, a You tab switched to) rises at once, and a widget already on screen never replays it. Under Reduce Motion they simply appear. Reuse `RiseIn` for a new entrance rather than a new animation.
- **A row swipes left to delete** (`SwipeToDelete`, `design/SwipeToDelete.tsx` -- the Food Library's own foods, recipes and saved meals): the row follows the finger and settles open or shut (instant under Reduce Motion), showing a quiet destructive **Delete** behind its right edge -- a `trash-2` glyph over "Delete" in `destructive`, on the row's own surface, never a filled red block. Delete always asks first in an alert. One row is open at a time; a tap on an open row, or swiping it back, closes it. The swipe is never the only way: the row offers the same Delete as an accessibility action (`ListRow`'s `accessibilityActions`), and its edit form keeps its own.
- **A carousel moves on by itself** (`AutoCarousel`, `design/AutoCarousel.tsx` -- Feed's Top Sets and the live workout's Last Time's Sets): one slide in view, paged by swipe, advancing every 3.5 seconds and wrapping, held still while dragged and while its page isn't in view, jumping instead of sliding under Reduce Motion, with a row of 6pt dots (`textPrimary` for the one showing, `textMuted` the rest). One slide shows on its own, with no dots. Never use it for anything typed into: today's set rows stay put.
- **A bar of the way there glides** (`AnimatedBar`, `design/AnimatedBar.tsx`): it fills in from empty when it first appears and springs to its new length when its figure changes (no overshoot, never past full), on the native driver -- the fill is the track's full width slid out of view, so its rounded end is never squashed. 4pt for a row's bar, 8pt for a widget's one figure, on a `surfaceRaised` track, hidden from screen readers (the figure beside it says it). Under Reduce Motion it is simply drawn at its length.
- Compose a screen from `Screen`, then `Section`s of `ListRow`s and `Stat`s; reach for an `AppCard` only for something the user taps or a set of facts that belong together (§10, §17).
- Import `Text` from `design/Text` for every string, so it renders in Plus Jakarta Sans (§5).

**Don't:**

- Don't hardcode a hex color, font size, spacing value, or radius that duplicates an existing token.
- Don't introduce a second "success" or generic "warning" color — the brand accent and destructive red are the only two semantic colors in the system.
- Don't add a second icon library alongside Feather.
- Don't use JetBrains Mono for anything other than numeric readout values.
- Don't apply the `hero` card treatment to more than one card per screen.
- Don't build a new tabs/segmented UI from scratch — reuse `SegmentedControl`, or (for a small fixed set that should read as one full-width, icon-over-label, underline-selected bar) `UnderlineTabs`.
- Don't let a selected tab/segment change size, weight, or padding — only color (§12).
- Don't add light-mode-conditional styling (§2).
- Don't invent a new disabled-state visual treatment beyond `opacity: 0.5`.
- Don't give every element a glass treatment — buttons, inputs, badges, and chart components stay as documented in their own sections (§3b). Glass is for major/structural surfaces, not small or simple content.
- Don't use the `chrome` (blurred) glass variant for anything that can appear more than once on screen at a time — reserve real blur for the single persistent nav/drawer/sheet instance; everything else uses the unblurred `surface` variant (§3b).
- Don't reintroduce background themes, colour customization or per-screen backgrounds — the one background (§3a) and the one accent (§3) are deliberate.
- Don't give a card another card: never nest an `AppCard` inside an `AppCard` (§10). Group with spacing, a hairline or a `ListRow` instead.
- Don't write a `fontFamily`/`fontWeight` pair by hand for ordinary text — use a `typeScale` token, or a bare `fontWeight` and let `Text` resolve it (§5). Never import `Text` from `react-native`.
- Don't add a second bottom navigation, or a screen-owned copy of the tab bar (§11).
- Don't hand-roll a button, list row, screen frame, section heading or loading placeholder — use `Button`, `ListRow`, `Screen`, `Section` and `Skeleton` (§8, §17).
- Don't make an interactive element smaller than 44pt to hit (§19) — extend its `hitSlop` if the visible size must stay small.
- Don't size a layout to fit its text at one font size (a fixed height, a `flexShrink` squeeze pool) — text scales with the user's Dynamic Type setting, so a layout that can't grow will clip.
